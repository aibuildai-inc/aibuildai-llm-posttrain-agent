# Principle 12: Pitfalls in checkpoint selection

**Layer**: Cross-cutting. Read before committing any checkpoint-selection plan.

**Source**: This file collates the failure modes that the other eleven principles either prevent or exist to repair. Each pitfall cites the principle that addresses it.

## The seven pitfalls

### 1. Per-fold cherry-pick

**What it looks like:** Manually choosing different epoch / checkpoint per fold based on inspecting the val curve fold-by-fold (e.g., fold_0 → epoch_7, fold_1 → epoch_14, fold_2 → public-LB-best).

**Why it fails:** The customization is driven by val-set inspection → direct val overfitting. The K-fold mean conflates K different estimators and is no longer interpretable as the generalization of any rule.

**Fix:** Principle 09 (fold-consistent selection rule). Commit to one rule in the plan, apply identically.

### 2. Max-attempt OOF selection

**What it looks like:** Aggregator pulling the single attempt with highest OOF per design into the cross-design ensemble.

**Why it fails:** `max` of N noisy observations has positive bias σ·√(2 log N). The reported OOF of the selected attempt is optimistically biased; private-LB rarely matches.

**Fix:** Principle 10 (top-K attempt aggregation). Average across top-K attempts; for N ≥ 20, prefer Principle 11 (Caruana selection).

### 3. Public-LB checkpoint tuning

**What it looks like:** Submitting different checkpoint variants and choosing the one with the highest public-LB score.

**Why it fails:** Public-LB is a tiny held-out set and gets overfit fast. Optimal checkpoint by public-LB rarely matches optimal by private-LB; the gap is often the deciding factor in competition rankings.

**Fix:** Trust OOF as the primary metric. Use public-LB as a 1-bit sanity check ("is this in the right ballpark"), not for selection.

### 4. Recipe-fold inconsistency

**What it looks like:** Selecting a recipe (lr, dropout, etc.) by reading the score of the BEST single fold rather than the K-fold mean.

**Why it fails:** Same winner's curse, applied at the recipe layer. The "best fold" of any recipe is biased optimistically; comparing recipes by best-fold is comparing biased estimates.

**Fix:** Compare recipes by mean-CV with std as tie-breaker. When two recipes have similar mean-CV but different std, prefer the one with smaller std (more stable across folds).

### 5. Weight-averaging snapshots from different basins

**What it looks like:** Last-N or top-K weight averaging applied to snapshot-ensemble cycle-end checkpoints.

**Why it fails:** Snapshot ensemble cycle-ends sit in DIFFERENT basins by construction (warm restarts are designed to escape basins). Weight averaging across basins produces a point in a non-convex region between basins, which is worse than any individual snapshot.

**Fix:** Snapshot ensembles must be PREDICTION-averaged (Principle 06 + Principle 07), not weight-averaged. Use weight averaging (Principles 02, 03) only for iterates within one basin.

### 6. Stale BatchNorm statistics after weight averaging

**What it looks like:** Deploying SWA / last-N / top-K weight average without one forward pass over training data to refresh BN running stats.

**Why it fails:** BN running statistics (mean, var per feature channel) were collected during the trajectory, not the average. The averaged weights expect different statistics; the mismatch typically wipes out the entire gain from averaging.

**Fix:** PyTorch `torch.optim.swa_utils.update_bn(loader, model)` after averaging. Required for any model with BatchNorm; harmless to call on LayerNorm-only models.

### 7. Different fold splits across attempts of the same design

**What it looks like:** Some attempts of one design use 5-fold, others use 10-fold, then their OOF is averaged as if comparable.

**Why it fails:** Per-sample OOF held-out semantics still hold (each sample's prediction comes from a fold that excluded it), but the averaging treats two different statistical estimators as one. The pooled OOF is no longer a valid CV-safe feature for downstream stackers.

**Fix:** Lock the `random_state` and protocol per design. The data manifest captures `(n_splits, random_state, protocol)` per fold; principle 10 averages only over attempts that share the same fold-split protocol.

## Summary

If you find yourself doing any of the seven, stop. Each maps directly to a fix in this playbook. Most are caught at audit time by the Judge's `data_leakage` integrity check, but the cheaper path is to avoid them in the first place.
